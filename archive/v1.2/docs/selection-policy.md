# 选择与长期维护规则

## 先区分四个判断

1. 是否有独立价值，值得原创介绍和链接导航。
2. 某环境是否满足许可、依赖、工具版本及权限，适合安装/采用。
3. 哪个版本和场景已完成真实运行验证。
4. 是否取得复制、修改或再分发第三方材料的权利。

这四项互不替代。平台专项、合理工具依赖和专有许可不自动否定导航价值；公开可读也不自动授予提取、运行或分发权。受限参考只写原创介绍、原始链接和限制，不给外部安装执行方案。

## 选择与比较

- 回到具体原始 SKILL.md、维护方、目录和完整 Commit；不要把 Awesome 合集、CLI、MCP 服务或管理器本身当单项 Skill。
- Stars、官方身份和榜单仅作来源/发现证据，不代替质量判断；个人是否安装同类工具不决定公开资源价值。
- 关注触发条件、任务边界、资源/脚本/依赖、网络和写入、失败处理及维护成本。支持按需加载，避免默认引入整套框架。
- 对近似候选比较：问题、功能边界、独特优势、平台/运行条件、许可/权限/成本、已验证与未知、何时选谁。不同 Office 格式、性能与架构、排障与安全审查可并列。
- 单纯复制、改名或缺少独立价值的包装不重复入库。不为“避免重复”强行只留一种优秀路线，也不为凑数弱化限制。
- 安全与许可独立判断，不能用质量总分抵消未解决重大风险。导航能清楚披露的采用限制与无法说明的重大风险要分开处理。

精选、按需/专项、参考是选择层级，不是实测等级；“并列”是互补关系，不自动等于精选。受限参考由 navigation_scope 单独标记，不泛化成普通可安装条目。

## 新增与变更

1. 单项提案记录原始目录、维护/作者依据、完整 Commit、许可与链接、用途、依赖、网络/文件权限和风险。
2. 提供相关同类比较，说明独立价值和适用场景；未知版本或许可范围保留未知。
3. 对必要资源和依赖做有界静态审阅。Skill、工具发行和依赖锁分别记录；同一版本号不能掩盖实现不同。
4. 按[验证规则](validation.md)区分 E1、E2 的材料/结果类别、E3、E4；仅有示例或测试源码不写“通过”。
5. 同步 catalog、README 分类表和 docs/skills；必要时更新比较、采用限制、许可说明和 schema。新增可选字段优先保持旧记录可读。
6. 针对实际变更一次核对 ID、数量、Commit、schema、链接、许可边界与敏感内容，人工审核后再合并/发布，不重复审计全部上游。

## 版本记录、暂停与回滚

保留 Git 提交中的旧目录数据、来源与验证范围；新版本先说明差异与影响，不将旧结果搬成新版本通过。除非有针对性依据，不改写旧条目的固定 Commit、许可和已确认验证事实。

发现来源失效、许可冲突、隐式安装/自动更新或敏感数据外发、无法解释的版本漂移、重大缺陷/失维护时，暂停相应采用建议或改为有边界的参考，记录公开理由。撤下/替换须人工决策，保留旧基线；不能以“更新”掩盖历史问题。

公开仓库回滚通过恢复明确的旧提交/单项数据与文档完成，并重新核对受影响统计，不改上游、不删除用户 Skill 或客户端配置。资源采用后的单项回滚见[获取与回滚](installation.md)。

## 数据与内容边界

catalog.json 是导航数据，不是数据库或安装系统；id 稳定唯一，upstream.commit 为完整 SHA，runtime_candidates 是候选而非配对认证。缺省 navigation_scope 不表示自动获得安装或分发权。

原创导览的 CC BY 4.0 与第三方 MIT、Apache-2.0、CC BY-SA 4.0 或专有条款分别处理。只公开元数据与原创评述，不提交私有审计日志、缓存、业务文件、个人路径、凭据或第三方源码镜像。网站、同步服务和安装器不属于本项目当前范围。
